# Shared Interfaces

These five formats are how the components talk to each other. If they're stable, the components can be built independently and in parallel. Design and version them first (Phase 0).

All of them live as files in the prototype repo under `design/`, except annotations, which live in the comment service and are exported to files at handoff.

> **Source of truth:** the JSON Schemas in [`packages/contract/schema/`](../../packages/contract/schema/). The sketches below are illustrations; where they differ, the schema wins. Refinements made while writing the schemas are listed in [ADR 002](../decisions/002-schema-tooling.md).

---

## 1. Design contract — `design/contract/`

The single source of truth for what a prototype may use.

```
design/contract/
  contract.json        # metadata: version, sources, schemaVersion
  tokens.json          # design tokens (W3C DTCG format)
  components/          # one manifest file per component
    button.json
    input.json
  rules.md             # human + AI readable do's and don'ts
  decisions.json       # decision log from intake
  gaps.json            # things not yet covered
```

Component manifest (sketch):

```json
{
  "name": "Button",
  "source": "production",            // production | figma | generated
  "confidence": "high",              // high | medium | low
  "import": "@/kit/Button",
  "props": {
    "variant": { "type": "enum", "values": ["primary", "secondary", "ghost"] },
    "size":    { "type": "enum", "values": ["sm", "md", "lg"] },
    "disabled": { "type": "boolean" }
  },
  "states": ["default", "hover", "focus", "disabled", "loading"],
  "rules": ["One primary button per view"],
  "mapping": {
    "production": { "path": "src/ui/Button.tsx", "export": "Button" },
    "figma": { "componentKey": "abc123" }
  }
}
```

`mapping` is what lets implement-handoff translate prototype components back to production code.

Schema: JSON Schema in `packages/contract/schema/`. Validated by `kit validate --contract`.

## 2. Flow manifest — `design/flows.json`

Generated by `kit export-flows` from the prototype's route and fixture registry. The canvas reads only this file, so the canvas never needs to understand the prototype's code.

```json
{
  "schemaVersion": 1,
  "commit": "a1b2c3d",
  "screens": [
    {
      "id": "checkout.payment",
      "route": "/checkout/payment",
      "title": "Payment",
      "states": [
        { "id": "default", "fixture": "default", "title": "Empty form" },
        { "id": "card-declined", "fixture": "card-declined", "title": "Card declined" }
      ]
    }
  ],
  "flows": [
    {
      "id": "checkout",
      "title": "Checkout",
      "nodes": ["cart.default", "checkout.shipping.default", "checkout.payment.default", "checkout.payment.card-declined"],
      "edges": [
        { "from": "checkout.payment.default", "to": "checkout.payment.card-declined", "label": "Submit, declined" }
      ]
    }
  ],
  "status": { "checkout.payment.card-declined": "in-review" }
}
```

Frame URL convention: `{baseUrl}{route}?fixture={fixture}&kit-frame=1`
(`kit-frame=1` tells the prototype to hide dev chrome and enable the annotation bridge.)

**Review status.** `status` maps a node to `exploring` (the default, so it's never written), `in-review`, `approved` or `handed-off` ([ADR 014](../decisions/014-frame-status.md)).
- It's set with `kit status`, the `set_status` MCP tool, or the canvas while running locally.
- `kit export-flows` keeps it for nodes that still exist.
- It doesn't count when checking whether `flows.json` is out of date with the code.

**Where the canvas reads it.** A running or built prototype serves this file at `/__kit-data/flows.json`. A built prototype may also serve `/__kit-data/snapshots.json`, a snapshot manifest (`snapshots.schema.json`):

```json
{
  "schemaVersion": 1,
  "commit": "a1b2c3d",
  "viewport": { "width": 1280, "height": 800 },
  "frames": { "checkout.payment.card-declined": "snapshots/checkout.payment.card-declined.jpg" }
}
```

**Frame bridge.** A prototype in frame mode posts these messages to its parent window (types in `@cogitato/contract/browser`, `bridge.ts`):
- `kit:state {node}` on load and after every move between states;
- `kit:rects`, `kit:hover` and `kit:select`, for anchoring comments.

The canvas accepts them only from its own iframes, on its own origin.

## 3. Annotation anchors — `data-kit-id`

Every interactive or meaningful element in the prototype carries a stable id:

```html
<button data-kit-id="checkout.payment.submit">Pay now</button>
```

Rules:
- Format: `{screenId}.{elementName}`, lowercase, dot-separated.
- Stable across edits. Renaming is a deliberate action (the reviewer agent flags renames that would orphan comments).
- Enforced by the validator: interactive elements without `data-kit-id` fail validation.

A comment's full anchor = `screenId + stateId + kitId + commit`.

## 4. Annotation model — comment service, exported to `design/annotations/`

```json
{
  "id": "ann_123",
  "anchor": {
    "screen": "checkout.payment",
    "state": "card-declined",
    "kitId": "checkout.payment.error-banner",
    "commit": "a1b2c3d",
    "fallbackRect": { "x": 0.1, "y": 0.2, "w": 0.8, "h": 0.1 }
  },
  "type": "intent",               // intent | spec | question | feedback
  "status": "open",               // open | resolved | archived
  "author": "user_1",
  "body": "Error copy should say what to do next, not just what went wrong.",
  "replies": [],
  "createdAt": "2026-11-01T00:00:00Z"
}
```

`fallbackRect` (relative coordinates) keeps comments placeable if an element disappears; such comments are marked "detached" in the canvas.

Exported files wrap the list with a version: `{ "schemaVersion": 1, "exportedAt": "...", "annotations": [ ... ] }`.

At handoff, `intent` and `spec` annotations and resolved `question`s are exported into the spec. `feedback` is archived.

## 5. Handoff spec — `design/handoff/{initiative}/spec.md` + `spec.json`

Markdown for humans, JSON for the developer's Claude Code.

Sections (from the concept doc):
1. Intent
2. Flow map and state inventory (links to canvas frames)
3. Component usage: reused / modified / new (generated from contract + code scan)
4. Data and behavior
5. Resolved annotations
6. Open questions
7. Acceptance criteria
8. Trust boundary: "layout and component composition are trustworthy; data handling and logic are not."

---

## Versioning

Each format carries `schemaVersion`. The kit CLI refuses to run against a newer schema than it knows and offers a migration for older ones.
